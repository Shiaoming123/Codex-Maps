# Codex Maps MVP 实施计划

**目标：** 先交付一个真正可用的 Session 地图核心与独立管理器；Codex 原生内嵌页和共享副屏作为单独的宿主集成门禁，不在缺少受支持挂载 API 时伪装成交付。

**架构：** Codex 当前宿主及其 App Server 是唯一会话事件源；宿主适配层把同一份快照、事件和命令能力暴露给共享状态仓库，再由内嵌页与副屏窗口消费。核心领域模型、事件归并和 UI 保持跨平台，壳层注入、进程、路径及打包能力按操作系统隔离。

**技术栈：** TypeScript、React、Electron、Codex App Server JSON-RPC、Electron IPC/preload bridge、Vitest、Playwright。独立模式由一个 Electron main process 管理；未来 Native Gate 通过后，内嵌页和副屏也必须由同一个 Host Bridge owner 管理。

**规格：** 本文件的“全局约束”“MVP 范围”和各纵向切片验收条件构成自包含规格。

## 2026-08-22 实施状态

当前结论已能拆开判断：**产品核心 GO；当前 Codex Desktop 原生宿主发布 NO-GO。** Session 地图、关系模型、实时 Store、独立管理器和安全操作语义有公开 App Server 合同支撑，可以继续实施。当前 build 虽存在内部 Bridge，却没有公开插件 route/window 挂载合同，第三方页面也不能自行获得 Codex preload；因此“左侧原生页 + 宿主副屏共享现有 request client”不能进入当前公开 MVP。

已落地：

- `SessionMapModule.observe({ kind: "overview" })` 的稳定快照边界。
- App Server initialize/initialized、`thread/list` 全量分页、重复边界校验和最小状态归一化。
- 内存协议适配器、生产 stdio 适配器、跨进程 JSONL 测试和本机无内容 smoke。
- 目标 Desktop build 生成合同核对；当前稳定合同支持 delete 与 Section，experimental 合同支持项目和 parent/ancestor 关系，原生 pin 仍是 Host Bridge 私有能力。所有写入口在运行时验收前保持 fail-closed。
- `HostBridgeModule` 合同切片：单 attach、双 renderer lease、同一 snapshot、独立释放、未知 fingerprint fail-closed，以及 exact thread navigation 回执核对。
- Desktop bundle envelope 探针：确认 `connect-app-host` 由 Codex preload 转发到私有 IPC；官方插件 manifest 没有 native route/window 字段。

尚未落地：

- 受支持的 Codex Desktop 外部挂载点；当前没有公开 route/window API，production adapter 停在 fail-closed。
- App Server 通知、重连、超时、server request、结构化错误和 mutation 不确定结果语义。
- 实时 Session Store、React 一级/二级页和任何写操作。

下一批开发改为双轨：核心轨继续完成 CM-002 客户端生命周期、CM-003 Store 和只读地图 UI；宿主轨只维护 fingerprint/能力探针并等待受支持扩展点。独立模式只能对自己拥有的 App Server 声称实时和可写；当 Codex Desktop 是 owner 时显示状态未知并关闭 mutation，不启动第二 App Server 冒充同源。

### 可交付层级

1. **Map Reader（当前可落地）：** 独立只读地图、搜索/分组/关系与详情；对其他进程拥有的活跃状态明确显示 unknown。
2. **Map Operator（可落地）：** Codex Maps 自己拥有 App Server 的独立模式，提供实时状态与经验证的管理动作。
3. **Codex Native（当前受阻）：** 左侧入口、精确原生跳转、宿主创建副屏并借用 Desktop request client；只有 Host Integration Gate 重新通过后发布。

## 全局约束

- 首发支持目标是 **Windows x64**；Windows x64 的完整端到端验收未通过，不得宣称 MVP 可发布。
- 核心包必须跨平台：领域模型、协议映射、状态归并、查询和共享 UI 不得直接依赖 Win32、注册表、盘符或 Windows 路径语义。
- 验证顺序固定为：Windows x64 首发 → macOS 第二验证 → Linux preview 第三验证。这里仅表示依赖顺序，不承诺开发或发布日期。
- WSL 单列为“Windows 宿主下的运行环境兼容”，不等同于 Linux 桌面版本，也不与 Linux preview 合并验收。
- 内嵌页和副屏窗口必须共享同一个 `sourceId`、同一条事件流和同一份带版本号的状态仓库；两种界面不得分别启动 App Server。
- Codex 已经拥有 App Server 时，Codex-Maps 只能复用该实例的 IPC/事件能力；不得为了获得实时状态再启动第二个 App Server。
- 壳层注入必须 **fail-closed**：Codex 版本、目标文件哈希、注入锚点数量或宿主接口任一不匹配时，停止注入并输出可诊断错误；不得模糊匹配、部分注入或继续启动一个看似可用但数据源不一致的页面。
- 不直接修改 Codex 的会话存储文件；所有读取和写操作都必须通过已验证的 App Server 协议或宿主接口完成。
- 会话状态分为两条独立轴：执行状态（如运行、等待、空闲、失败、断连）与任务状态（如进行中、阻塞、完成、归档、未知）。`turn completed` 只能结束本轮执行，不得自动推断整个任务已完成。
- 快照与事件必须携带 `sourceId` 和单调递增的 `revision`。客户端发现来源变化、版本倒退或事件缺口时，必须丢弃增量并重新拉取完整快照。
- 无法从协议获得的数据必须显示“不可用”，不得推测子 Agent、Token、上下文长度、任务完成度或项目归属。

## MVP 范围

### 包含

- 会话列表、分页加载、搜索，以及按项目、置顶、普通、归档和实时状态筛选或分组。
- 实时展示执行状态；在协议明确提供任务/Goal 状态时，独立展示任务状态。
- 一级项目泳道管理页（列表/卡片降级）与二级详情页；详情包括当前计划/进度、最近输出概览、Token/上下文用量、父子/分支关系摘要和子 Agent 摘要，缺失字段明确降级。
- 打开指定会话，以及目标 build 明确支持的重命名、置顶/取消置顶、归档、取消归档和删除；能力缺失时隐藏入口并在兼容矩阵中说明。当前 Desktop 合同允许继续验证删除与项目/Section，置顶仍需宿主侧栏桥接。
- 独立窗口复用共享核心；原生左侧入口和借用 Desktop 同源的副屏属于 `Codex Native` 门禁，不计入当前公开 MVP 完成度。
- Windows x64 独立模式支持证据；macOS 第二验证；Linux standalone preview 第三验证；WSL 独立兼容结论。原生宿主支持单独声明。

### 不包含

- 可编辑的完整关系图、拖拽重组分支或合并会话。
- 基于对话正文猜测阻塞原因的鱼骨图；MVP+1 仅在有明确等待、审批、错误或依赖事件时启用诊断视图。
- 跨多台设备、云端同步、多用户协作和远程控制。
- 直接编辑项目根目录、项目颜色/图标或其他实验性项目 API；MVP 只读取并展示协议明确返回的项目元数据。
- 同时聚合 Windows 与 WSL 两个独立 Codex 数据源。一个运行实例只允许激活一个会话来源。

## 计划中的实现边界

以下路径是后续实施将创建或修改的边界；撰写本计划本身不改动这些文件。

- `packages/session-store/`：纯 TypeScript 领域类型、双轴状态机、快照/事件 reducer、查询和权限规则。
- `packages/app-server-client/`：App Server JSON-RPC 类型、方法适配、通知规范化和协议契约测试。
- `packages/ui/`：一级页、二级页、状态组件、确认对话框和共享路由；不持有 App Server 进程。
- `packages/codex-host/`：Codex 壳层能力探测、版本/哈希校验、内嵌导航与页面注入。
- `packages/platform/`：路径、窗口、快捷键、通知、安装发现和打包的系统适配。
- `apps/desktop/`：唯一 Host Bridge、命令队列、内嵌宿主接线与副屏 BrowserWindow；两个 renderer 只通过受控 preload API 连接共享仓库。
- `tests/fixtures/app-server/`：脱敏 JSON-RPC 快照、事件序列、断线、乱序、错误及写操作响应。
- `tests/contract/`：协议与状态归并契约测试。
- `tests/e2e/`：内嵌页、副屏、写操作、壳层注入和平台行为端到端测试。
- `scripts/verify-single-source.mjs`：验证两个界面只消费一个 App Server/事件源。
- `scripts/verify-shell-injection.mjs`：验证宿主版本、文件哈希、唯一锚点和 fail-closed 行为。

## 依赖顺序

```text
切片 0 技术门禁
  → 切片 1 只读快照
  → 切片 2 实时状态
  → 切片 3 一级/二级 UI
  → 切片 4 安全写操作
  → 切片 5 双形态宿主
  → 切片 6 跨平台硬化
```

任一切片未达到退出条件时，后续切片只能使用固定 fixture 做界面预研，不得形成发布候选，也不得绕过失败门禁。

## 切片 0：宿主集成门禁——证明“可注入、可复用、仅一个事件源”

### 目标

在不写入真实会话的前提下，证明目标 Codex 版本能够安全挂载 Codex-Maps，并且内嵌页与副屏窗口可以复用 Codex 当前 App Server 的快照、通知和命令通道。此切片决定产品架构是否成立。

### 具体交付

- [x] 建立宿主能力探针，记录 Codex 版本、平台、架构、目标文件 SHA-256、可用内部 Bridge 证据和 App Server 所有权。
- [x] 定义最小 Host Bridge 契约，包含 fingerprint、`session.read`、`thread.navigate`、共享 SnapshotSource、renderer lease 和 owner-only dispose。
- [ ] 建立版本锁定的注入清单；只有“版本匹配 + 哈希匹配 + 锚点恰好一个 + 宿主契约完整”时才允许注入。
- [x] 实现核心 fail-closed 合同：未知 fingerprint 在 adapter attach 前拒绝；不注册入口、不启动副屏、不启动备用 App Server。Desktop production adapter 仍未实现，因为当前没有受支持挂载点。
- [ ] 建立单事件源检测：给 App Server 子进程或现有宿主通道分配稳定 `sourceId`，记录进程 PID/通道 ID，拒绝第二所有者。
- [ ] 增加脱敏协议录制器，只记录方法名、事件类型、线程假 ID、revision 和时间，不记录用户消息正文或凭据。

### 独立验收

- [ ] 在受支持的 Windows x64 Codex 测试副本上运行 `npm run verify:shell-injection`，结果为 `compatible=true`，并输出唯一注入锚点和完整 `HostCapabilities`。
- [ ] 同时打开探针内嵌客户端与探针副屏客户端，运行 `npm run verify:single-source`；结果必须显示两个客户端 `sourceId` 相同，App Server 所有者数量为 `1`。
- [ ] 修改 fixture 中的 Codex 版本、目标文件哈希和锚点数量，三组测试都必须拒绝注入；拒绝前后测试副本文件哈希保持不变。
- [ ] 在 Codex 已运行时启动副屏探针，进程检查必须证明没有新增 App Server；若共享通道不可用，副屏显示“宿主不兼容”并停止。
- [ ] 全程不调用 `thread/name/set`、`thread/archive`、`thread/unarchive` 或 `thread/delete`，真实会话数据无变更。

### 明确退出条件

- **通过并进入切片 1：** 受支持 Windows x64 构建通过全部验收，且两个客户端能从同一个 `sourceId` 收到事件。
- **停止：** 无法复用宿主事件流、必须启动第二 App Server 才能实时更新、或无法稳定识别注入点。此时不得用“两个 App Server 最终一致”作为替代架构，也不得宣称内嵌 MVP 可行。
- **重新门禁：** Codex 升级后版本或哈希变化，必须回到本切片重新生成兼容清单；旧注入规则默认失效。
- **2026-08-22 当前判定：** 内存架构验收已通过；Desktop production attach、第二窗口注册和 exact-navigation 回执均未通过，故 `Codex Native` 停止，核心轨继续。

## 切片 1：只读快照——先让用户可靠地看到全部会话

### 目标

通过唯一宿主通道获得一致、可分页、可查询的会话快照，形成后续实时更新和 UI 的稳定读模型。

### 具体交付

- [ ] 为 `thread/list`、`thread/read` 及项目/分区只读接口建立显式协议类型和 fixture；未知字段保留但不进入业务判断。
- [ ] 实现全量分页加载、重复 ID 消除、归档分区、置顶/普通分区、项目归属、父子关系和缺失字段降级。
- [ ] 定义 `SessionSnapshot { sourceId, revision, generatedAt, sessions, projects, capabilities }`，由状态仓库一次性发布，不让 UI 拼接半完成分页。
- [ ] 实现本地搜索和筛选：标题、会话 ID、项目、根目录、归档状态和执行状态；搜索不得触发写操作。
- [ ] 给快照建立 Schema 版本；版本不兼容时清空缓存并重新拉取，不复用旧结构。
- [ ] 增加“只读安全断言”，测试期间任何写方法被调用即失败。

### 独立验收

- [ ] 使用包含 1,000 个会话、重复分页边界、已归档会话、无标题会话和多根项目的 fixture 运行 `npm run test:contract -- snapshot`；输出会话 ID 与 fixture 集合完全一致，无重复、无漏项。
- [ ] 搜索标题、会话 ID 和根目录时返回预期集合；Windows 大小写差异和路径分隔符不会制造重复项目。
- [ ] 断开分页中的任意一页时，仓库保留上一份完整快照并标记 `stale=true`，不会发布半份新快照。
- [ ] 在一次只读真实环境 smoke test 中，列表总数、归档筛选和随机抽取的 10 个 `thread/read` 结果与 Codex 本身一致。
- [ ] 协议调用日志中写方法计数为 `0`。

### 明确退出条件

- **通过并进入切片 2：** fixture 与真实 smoke test 均无重复、漏会话或错误归档；任何失败都能保留上一份一致快照。
- **停止：** 协议无法稳定分页、同一线程 ID 出现不可解释的冲突、或读取需要直接解析/修改 Codex 内部会话文件。

## 切片 2：实时状态——从快照演进为可观察的活动地图

### 目标

把唯一事件源的通知确定性归并到快照，使两个界面实时看到一致状态；断线或漏事件时自动回到完整快照，而不是猜测。

### 具体交付

- [ ] 定义标准事件 `SessionEvent { sourceId, revision, threadId, kind, payload, receivedAt }`，拒绝来源不匹配、revision 倒退和跨线程污染。
- [ ] 实现双轴状态 reducer：执行状态与任务状态分别更新；轮次完成只将执行状态转为空闲，只有明确 Goal/任务完成事件才能显示任务完成。
- [ ] 归并线程创建、名称变化、归档、取消归档、删除、轮次开始/完成、计划变化、Token 用量、错误和连接状态通知。
- [ ] 建立事件缺口策略：检测到 revision 跳号、重连或来源变化后暂停增量，拉取新快照，再从新 revision 继续。
- [ ] 给两个 UI 客户端广播同一个仓库 revision；客户端只渲染读模型，不自行解释原始 App Server 通知。
- [ ] 建立可重放事件 fixture，覆盖乱序、重复、延迟、断线、宿主重启和未知事件。

### 独立验收

- [ ] 运行 `npm run test:contract -- realtime` 重放固定事件序列，两次重放产生字节级一致的最终快照。
- [ ] `turn started → turn completed` 后执行状态从“运行中”变为“空闲”，任务状态保持原值；只有显式完成事件才显示“已完成”。
- [ ] 同时连接两个测试客户端，所有事件后两端 `sourceId` 与 `revision` 完全相同，状态内容深度相等。
- [ ] 模拟丢失一个 revision：两端先显示“正在重新同步”，随后收到相同新快照；期间不得显示推测状态。
- [ ] 模拟宿主关闭：副屏显示“已断开”，不得启动 App Server；宿主恢复后通过重新快照恢复。

### 明确退出条件

- **通过并进入切片 3：** 双客户端在正常、乱序和断线场景下都收敛到同一 revision，且没有把轮次结束误标为任务完成。
- **停止：** 两个客户端需要各自订阅/解释原始事件才能工作，或丢事件后无法通过完整快照恢复一致性。

## 切片 3：一级/二级 UI——建立“先管理、再深入”的主流程

### 目标

提供清晰的一级总览与二级详情，让用户能在大量会话中快速发现状态、定位项目并打开目标会话；本切片保持只读。

### 具体交付

- [ ] 一级页默认使用项目泳道：项目为稳定泳道，Session 为节点，显示执行状态、目标状态、最近活动和权威关系摘要；同时提供列表/卡片降级，并支持搜索、项目/置顶/普通/归档筛选和需要关注视图。
- [ ] 状态视觉遵守双轴语义：运行使用动态指示，空闲使用中性状态，失败/阻塞使用可辨识警示，任务完成只来自明确任务状态。
- [ ] 二级页展示标题、项目、根目录、执行状态、任务状态、计划/进度、最近输出概览、Token/上下文、父线程、分支/子 Agent 摘要和最近更新时间。
- [ ] 若 parent/ancestor/spawned 关系能力可用，二级页提供最多两层的只读关系树；字段不可用时回退为摘要列表，不根据标题或正文推断连线。
- [ ] 缺失字段显示“不可用”及原因；不基于消息文本猜测任务进度、子 Agent 数或完成状态。
- [ ] “在 Codex 中打开”使用宿主提供的精确线程 ID，不以标题搜索替代。
- [ ] 实现键盘导航、焦点可见性、颜色之外的状态标识、缩放和窄窗口布局。

### 独立验收

- [ ] Playwright 使用固定快照完成“搜索 → 筛选项目 → 打开二级页 → 返回并保留筛选”的端到端流程。
- [ ] 在运行、空闲、失败、阻塞、完成、归档、断连和数据不可用八种 fixture 下做视觉快照，状态文案和图标语义与双轴状态一致。
- [ ] 仅键盘可完成一级页搜索、选择会话、进入二级页、返回和“在 Codex 中打开”。
- [ ] 点击“在 Codex 中打开”传给宿主的线程 ID 与当前详情线程严格相同；不存在匹配时显示错误且不打开其他会话。
- [ ] 本切片 UI 不显示可执行的重命名、置顶/取消置顶、归档、取消归档或删除按钮；协议调用日志写方法计数为 `0`。

### 明确退出条件

- **通过并进入切片 4：** 一级/二级核心流程在 fixture 和真实只读数据上可完成，状态无误导，键盘流程可用。
- **停止：** UI 需要直接访问 App Server、两个页面各自维护状态，或任何缺失数据被推测填充。

## 切片 4：安全写操作——让管理能力可用且可控

### 目标

通过唯一宿主命令通道安全提供重命名、置顶/取消置顶、归档、取消归档和删除；失败时不让两个界面出现虚假成功或永久分叉。

### 具体交付

- [ ] 建立命令层 `renameSession`、`setPinned`、`archiveSession`、`unarchiveSession`、`deleteSession`，每次调用携带 `sourceId`、线程 ID、发起时 revision 和幂等请求 ID。
- [ ] 重命名验证去除首尾空白并拒绝空标题；服务端失败时保留原名称并显示可重试错误。
- [ ] 归档和取消归档等待服务端确认事件；超时则重新拉取快照，不以本地乐观状态作为最终结果。
- [ ] 删除前展示精确线程 ID、标题、已知后代数量和不可恢复说明；要求输入当前标题或完整线程 ID 二次确认。
- [ ] 后代数量未知、当前 revision 过期、来源已切换或宿主能力不完整时禁用删除，先重新读取详情。
- [ ] 写成功后依赖共享事件更新两个界面；若服务端没有对应通知，则由命令层触发一次共享快照刷新，禁止每个界面单独刷新。
- [ ] 记录本地审计条目：时间、动作、线程假名/ID 哈希、结果和错误码；不记录会话正文。

### 独立验收

- [ ] 对一次性 fixture 依次执行重命名、置顶、取消置顶、归档、取消归档；两个客户端最终 revision 相同，且服务端状态与读模型一致。
- [ ] 删除确认输入错误时不发送请求；输入正确且后代数量已知时删除目标线程及其 spawned descendants，但不误删兄弟线程。
- [ ] 模拟写入权限不足、线程正在被其他进程占用、网络/IPC 中断和服务端超时；界面显示失败，重新快照后与服务端一致。
- [ ] 在 sourceId 变化或 revision 过期时提交写命令，命令层必须拒绝并要求刷新。
- [ ] 运行 `npm run test:e2e -- safe-mutations` 后，审计日志不包含消息正文、Token 或凭据。

### 明确退出条件

- **通过并进入切片 5：** 五组写能力均通过成功、失败、超时、过期和双客户端一致性测试；删除保护不能被键盘或直接 IPC 调用绕过。
- **降级但不冒充完成：** 若目标 Codex 版本不提供可靠删除语义，Windows MVP 可关闭删除能力并明确标为“不支持”，但不得将该构建描述为包含完整基本管理能力。
- **停止：** 写操作必须直接改会话文件、无法确认目标线程、或两个界面会产生互相覆盖的本地乐观状态。

## 切片 5：双形态宿主——同一产品、同一状态、两个窗口

### 目标

交付 Codex 左侧入口/内嵌页与可移动到副屏的独立窗口；二者共享同一宿主生命周期、状态仓库和命令通道。

### 具体交付

- [ ] 通过已验证注入清单增加 Codex 左侧 `Codex Maps` 入口和内嵌路由，注入代码只引用宿主适配接口，不读取私有存储文件。
- [ ] 由同一宿主创建副屏窗口；窗口可独立最小化、最大化、移动和恢复布局，但不拥有 App Server 生命周期。
- [ ] 两个 renderer 通过受控 Electron preload bridge 订阅同一状态仓库；握手校验 `sourceId`、协议版本和宿主实例 ID，renderer 不获得任意 IPC 或文件系统权限。
- [ ] 实现单实例与窗口恢复：重复打开副屏只聚焦已有窗口；关闭副屏不影响内嵌页和 App Server。
- [ ] 宿主关闭或升级导致注入失效时，副屏进入断连只读页，停止命令，不自行启动 App Server。
- [ ] 内嵌页与副屏复用同一套路由和组件；仅窗口导航、尺寸和快捷键由宿主适配层区分。

### 独立验收

- [ ] 在 Windows x64 测试副本中，从 Codex 左侧进入内嵌页，再打开副屏；进程与通道检测显示 App Server 所有者始终为 `1`。
- [ ] 任一会话状态变化在共享仓库收到事件后，两个窗口都推进到同一 revision；不得通过轮询各自修正差异。
- [ ] 在内嵌页重命名、在副屏归档同一测试会话，操作串行化且最终服务端状态、内嵌页和副屏一致。
- [ ] 连续触发十次“打开副屏”，系统中仍只有一个副屏窗口；关闭后重新打开能恢复上次显示器和尺寸，若显示器不存在则回到主屏可见区域。
- [ ] 使用哈希不匹配的 Codex fixture 启动，左侧入口和副屏均不出现，诊断报告明确指出失败项，宿主文件未改变。

### 明确退出条件

- **通过并进入切片 6：** 两种宿主形态均能完成只读、实时和安全写流程，并共享相同 `sourceId/revision`。
- **停止发布：** 内嵌注入在首发支持的 Codex 构建失败。仅 standalone 可作为开发预览，不得替代用户要求的内嵌 MVP。
- **停止并修复：** 副屏能在宿主断连后自行启动 App Server，或两个窗口出现不同 sourceId；这是架构缺陷，不接受重试掩盖。

## 切片 6：跨平台硬化——Windows 首发，macOS 次验，Linux preview，WSL 单列

### 目标

证明共享核心不依赖单一系统，同时把每个平台的宿主能力和支持声明限制在已有测试证据内。

### 具体交付

- [ ] 将进程发现、IPC、文件锁、路径标准化、窗口恢复、壳层探针和打包拆成平台适配器；`session-store`、`app-server-client` 和 `ui` 不导入平台适配实现。
- [ ] 建立核心 CI 矩阵：Windows x64、macOS、Linux 均执行协议、reducer、查询和共享 UI 测试。
- [ ] 建立 Windows x64 发布验收包，包含兼容 Codex 构建指纹、安装/卸载验证、单事件源报告、E2E 报告和 fail-closed 报告。
- [ ] Windows x64 通过后才进行 macOS 第二验证；macOS 必须重新完成壳层门禁、只读、实时、双窗口和安全写操作，不沿用 Windows 注入指纹。
- [ ] macOS 验证完成后才生成 Linux preview；Linux preview 默认只承诺核心与 standalone 能力，只有存在可验证 Codex 壳层时才单独开放内嵌适配。
- [ ] 为 WSL 建立显式模式：记录发行版名与原始 Linux 路径，由 Windows 宿主负责显示/打开映射；映射不确定时 fail-closed，不猜测盘符或发行版。
- [ ] WSL 模式仍复用 Windows 宿主当前唯一事件源；不得隐式在 WSL 内启动第二 App Server。需要 WSL 原生数据源的场景作为独立 profile 处理，MVP 不与 Windows profile 同时激活或聚合。
- [ ] 生成支持矩阵，每个平台只标记 `supported`、`preview` 或 `unsupported`，并链接对应验收产物。

### 独立验收

- [ ] **Windows x64 首发：** 切片 0–5 的真实环境 E2E 全部通过；安装和卸载不改官方 Codex 安装目录之外的文件；升级到未知 Codex 指纹时 fail-closed。
- [ ] **macOS 第二验证：** 核心 CI 通过，并在该平台目标 Codex 构建上重新通过单事件源、注入、实时、写操作和双窗口测试后，才可标记 `supported`。
- [ ] **Linux preview 第三验证：** 核心 CI 与 standalone 测试通过，包明确标记 `preview`；未完成壳层注入门禁时不展示或宣传内嵌能力。
- [ ] **WSL 单列：** 使用至少两个发行版 fixture 验证路径展示、打开、根目录分组和不可映射错误；进程检查证明 Windows 内嵌页和副屏没有额外启动 Windows 或 WSL App Server。
- [ ] 在三类桌面系统的路径/锁/IPC fixture 中运行相同事件重放，最终领域快照完全一致；平台差异只存在于适配层输出。

### 明确退出条件

- **Windows x64 MVP 可发布：** Windows 项全部通过，发布包含可复核证据，并且未知壳版本默认拒绝注入。
- **macOS 可支持：** 仅在 Windows 首发门禁通过后，macOS 独立验收全部通过；否则保持 `unsupported`，不影响已验证的 Windows 构建。
- **Linux preview 可发布：** 仅在 macOS 第二验证完成后，核心与 standalone 验收通过并清楚标注 preview；内嵌能力未验收则保持关闭。
- **WSL 可声明兼容：** 路径映射和单事件源验收通过；否则明确标记 WSL `unsupported`，不做静默路径转换。

## Windows x64 Codex Native 候选总体验收门

只有同时满足以下条件，首发构建才算完成：

- [ ] 受支持 Codex 构建通过版本、哈希、唯一锚点和宿主契约检查；未知构建 fail-closed。
- [ ] 内嵌页和副屏使用相同 `sourceId`，App Server 所有者数量始终为 `1`。
- [ ] 只读快照无重复、漏项或半快照发布；断线能恢复到一致 revision。
- [ ] 实时状态不把轮次完成误判为任务完成，两个窗口在每次事件后收敛。
- [ ] 一级/二级流程、精确打开会话和所有已声明支持的管理操作通过 E2E；目标 build 缺失的能力已隐藏且兼容矩阵准确。
- [ ] 宿主关闭、IPC 断开、版本升级、写失败和显示器移除均有明确安全降级，不启动备用 App Server。
- [ ] 核心包在 Windows、macOS、Linux CI 上通过；对 macOS、Linux 和 WSL 的支持声明与各自证据一致。

## 执行与提交规则

- 严格按切片 0 → 6 执行；每片使用独立分支或独立提交序列，先通过本片测试再合入。
- 每个切片至少包含：契约测试、fixture、最小实现、真实环境 smoke test（平台允许时）和验收报告。
- 每次提交只包含当前切片文件；不得使用 `git add -A`，应显式暂存测试与实现路径。
- 验收报告必须写明运行命令、Codex 版本/指纹、操作系统/架构、通过项、失败项和跳过项；存在跳过项时不得写“全部通过”。
- 任一门禁失败时先记录证据并停止依赖它的后续实现；不得通过降低断言、忽略错误或复制数据源来制造通过结果。
